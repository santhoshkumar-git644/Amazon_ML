# Business Entity Resolution — Pipeline

Reproduces `output/matching_results.tsv` and `output/candidate_pairs.tsv` end to end
from the raw `dataset/train` and `dataset/test` TSVs. Pure Python/pandas/LightGBM,
no external services, geocoders or lookups are used anywhere (per the challenge's
fair-play rules) — only the provided training data.

## Approach in one paragraph

Business names/addresses share no common key across the three sources, so we (1)
normalize text (case/punctuation/legal-suffix folding), (2) generate a manageable
candidate set per Source-1 entity with multi-key inverted-index **blocking**
(shared rare name token, shared postal code, shared name prefix — each with a
document-frequency cutoff so common words/prefixes don't blow up the candidate
set), (3) compute pairwise similarity **features** (token/character fuzzy-match
scores, token-set Jaccard on name and address, postal/country/prefix agreement),
(4) train a **LightGBM** binary classifier on candidate pairs labeled from
`train_ground_truth.tsv`, and (5) tune a single probability **threshold** on a
held-out slice of Source-1 entities to maximize the macro F_0.5 the challenge
scores on. See `../../Documentation_template.md` (filled in, at the submission
zip root) for the full write-up, EDA findings and error analysis.

## Directory layout

```
src/
  normalize.py     text cleaning (name/address normalization, postal extraction)
  blocking.py      inverted-index candidate generation (blocking)
  features.py      pairwise similarity feature computation
  scoring.py        macro F_0.5 scorer (matches the challenge's metric)
  prepare.py       normalizes + caches each raw source file once (work/cache/*.parquet)
  train_model.py   builds train candidates/features, trains the model, tunes threshold
  predict.py       builds test candidates/features, scores them, writes output/*.tsv
```

```bash
cd student_resource   # this file's grandparent directory: has dataset/, output/, etc.
python3 -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r code/business_entity_resolution/requirements.txt
```

## Run (end to end)

All commands are run **from `student_resource/`** (so relative paths in the raw
problem statement's own instructions — `dataset/...`, `output/...` — line up).

```bash
# 1. Normalize + cache every raw source file (one-time cost, ~10 min on the full data;
#    re-run is instant unless a raw file changed — cache is keyed on file mtime).
python3 code/business_entity_resolution/src/prepare.py

# 2. Train the classifier on dataset/train/*, tune the threshold on a held-out
#    15% slice of Source-1 training entities, save model + threshold to work/.
python3 code/business_entity_resolution/src/train_model.py

# 3. Score dataset/test/* and write output/matching_results.tsv + output/candidate_pairs.tsv.
python3 code/business_entity_resolution/src/predict.py

# 4. Validate the output format before submitting.
python3 utils/validate_submission.py \
    --matching output/matching_results.tsv \
    --candidate output/candidate_pairs.tsv \
    --test-dir dataset/test
```

`work/` holds intermediate artifacts (normalized-file cache, the trained model,
tuned threshold + metadata) and is not required for grading — everything in it is
regenerated by the three commands above.

## Design notes / why it scales

- **No O(n·m) pair comparisons.** Source-1/2/3 are ~1.7-5M rows each; a full cross
  product per (Source-1, Source-2 or 3) pair would be tens of trillions of
  comparisons. Blocking uses an inverted index (token/postal/prefix -> row
  positions) and only pairs rows that share a key, with a bucket-size cutoff
  (`blocking.MAX_BUCKET_PRODUCT`) that skips keys too common to be discriminative
  (e.g. a generic word, a very frequent prefix).
- **Row positions, not ID strings, in the hot path.** The candidate/feature table
  (tens of millions of rows during training) carries `int32` row positions and
  `int8`/`float32` features instead of entity_id strings, which are only
  re-attached for the rows that make it into an output file. This keeps the
  pipeline usable on a machine with a few GB of RAM.
- **Threshold tuned on the actual metric.** Because F_0.5 is a precision-heavy,
  per-entity macro average (and singletons matter a lot), the classifier's raw
  probability output is calibrated to a single decision threshold by directly
  maximizing macro F_0.5 on held-out Source-1 entities, not by optimizing a proxy
  like log-loss or accuracy.
